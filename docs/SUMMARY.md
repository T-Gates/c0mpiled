# Human Check — 정리 (2026-11-09)

> 범례: **[사실]** 코드·테스트·출처로 확인 / **[가설]** 원리상 추정, 실측 안 함 / **[조사]** 웹 검색, 대부분 회사 자체 발표 / **[미승인]** 제안만 하고 결정 안 함

## 1. 한 줄 요약

웹캠 앞의 사람이 **실제로 화면 빛을 받는 입체 얼굴·손**인지, 그리고 **화면이 가려지거나 변조되지 않았는지**를 무작위 화면 빛의 반사로 확인한다. 기술 자체는 새롭지 않다(iProov가 상용화). 해커톤 가치는 "구글 손동작 캡챠를 뚫은 공격을 브라우저에서 바로 막는다"는 실증과, 반사로 **화면 오버레이·가림**까지 진단한다는 각도다.

## 2. 지금 동작하는 것 (`CONTRACT.md` v1.5) [사실]

| 단계 | 하는 일 | 막으려는 공격 |
|---|---|---|
| 손 모양 | 무작위 손 모양 3개, 손가락 관절 각도로 판정 | 정지 사진·녹화 영상 |
| 색 반사 | 흰→색→흰 ×3 (R/G/B 무작위 순서, 500ms), 손바닥·얼굴의 색 비율 변화 | 가상 카메라(OBS)·녹화 영상 |
| 입체 | 2×2 사분면 하나씩 켜고 좌우 뺨 밝기 차이(H) | 종이·휴대폰 화면 사진(평면) |
| 진단 | 반사 패턴으로 실패 원인 표시: 정상 / 반사 없음 / 화면 일부 가림 / 색 변조 / 색 반사 약함 / 평면 물체 / 데이터 부족 | 오버레이·필터·가림 설명 |

- 최종 통과 = 손 모양 ✓ AND 손 색 ✓ AND 얼굴 색 ✓ AND 얼굴 입체 ✓. 진단은 설명용이고 통과 조건이 아니다.
- 전환 연속성 판정은 진짜 손도 떨어뜨려서 제외했다.
- 데이터 수집: 라벨 `real` / `phone` / `obs` / `block`으로 라운드 기록 → JSON 다운로드 → `node tools/calibrate.mjs <파일> --write` → `calibration.json` 자동 적용.
- 검증: `node --test` **180/180 통과**(2026-11-09 확인). **실제 카메라 데이터는 0건** — 기준값(minDelta 0.004, minSwingH 0.05, blockDrop 0.08 등)은 전부 어림값이다.
- 실행: `python3 -m http.server 8000` → http://localhost:8000

## 3. 무엇을 막고 무엇을 못 막나

| 공격 | 예상 결과 | 근거 |
|---|---|---|
| 종이 사진 | 색 반사는 통과할 수 있음, **입체에서 걸림** | [가설] 종이도 빛을 반사하지만 평평함 |
| 휴대폰 화면 사진·영상 | 걸림 | [가설] 화면 자체가 발광 → 반사 약함, 평면 |
| OBS 가상 카메라 + 녹화 영상 | **걸림** (반사 없음) | [가설] 무작위 순서를 미리 알 수 없음. 구글 reCAPTCHA는 이걸로 뚫림 [조사] |
| 사진으로 움직이는 아바타(LivePortrait 류) | 걸림 | [가설] 픽셀이 사진에서 와서 촬영 당시 조명 고정 |
| 실시간 얼굴 교체(Deep-Live-Cam 류) | **불확실 — 통과할 수 있음** | [가설] 공격자의 진짜 얼굴이 빛을 받고, 교체 모델이 조명·색을 옮겨 옴. 손은 교체 안 되므로 원래 진짜 |
| 무작위 순서를 읽고 반사까지 실시간 합성해 주입 | **못 막음** | 빛으로 풀 문제가 아님 → 주입 탐지·기기 증명 영역 (범위 밖) |
| 3D 마스크·마네킹 | 통과할 수 있음 | [가설] 입체이고 빛을 반사함 |
| 화면 오버레이(Cluely/Interview Coder 류) | 화면 넓은 부분을 가리면 진단 가능, 작거나 투명하면 어려움 | [가설] 소프트웨어로는 원리상 못 잡음(화면 공유·포커스에 안 잡힘) → 반사로만 접근 가능 |
| 두 번째 모니터·휴대폰·화면 밖 메모 | 못 잡음 | 화면 빛과 무관 |
| 검사 후 오버레이 띄우기 | 못 잡음 | 검사 순간만 확인 |

실시간 얼굴 교체에 대한 딜레마 [가설]: 교체 모델이 조명을 옮겨 오면 화면 가림도 함께 드러나고, 못 옮겨 오면 색·입체 판정에 걸린다. 실측 전까지는 가설이다.

## 5. 정답 기준을 어떻게 두나 (원칙)

1. **무엇을 볼지는 물리, 얼마나여야 하는지는 데이터.** 변화 방향·좌우 비대칭 부호는 원리로 정해지고, 기준값과 정확도(진짜를 떨어뜨리는 비율 FRR, 가짜를 통과시키는 비율 FAR)는 데이터로만 정한다.
2. **절대값 대신 모양.** 가림 판정은 구역별 반응을 그 라운드 합으로 나눈 비율로 본다. 거리·피부색·자동 노출·주변 조명 영향이 대부분 사라진다.
3. **정답은 세션 밖에서.** 사용자가 직접 보정하면 딥페이크 상태를 정상으로 등록할 수 있다. 정상 범위는 **팀이 직접 모은 `real` 데이터로만** 만들고, 사용자별 보정 단계는 두지 않는다. 제품에서 사용자별 등록이 필요하면 등록 자체를 더 강한 확인(대면·신분증) 아래서 한다.
4. **세션 안에서는 무작위.** 색 순서·구역 순서를 `crypto.getRandomValues`로 섞어 공격자가 반응을 미리 만들 수 없게 한다.
5. 가림 판정은 데이터가 쌓이기 전까지 **표시만** 하고 통과 조건에 넣지 않는다(전환 판정 오탐의 교훈).

## 6. 제안됐지만 아직 안 한 것 [미승인]

- **띠 스캔(1×4 세로 + 4×1 가로, 8단계)으로 2×2 사분면 대체.** 띠 면적이 사분면과 같아(1/4) 신호 세기는 유지하면서 4×4 위치까지 짚는다. 세로 띠 좌우 차이로 H, 가로 띠로 V를 그대로 계산 가능. 바깥 띠는 원래 약하므로 정상 모양은 데이터로 정해야 하고, 세로 띠는 얼굴이 중앙일 때 좌우 대칭 검사를 데이터 없이 쓸 수 있다. 전부 끈 기준 단계 1개 추가 필요. 띠 순서는 무작위.
- 색을 6색(60° 간격)으로 늘리고 판정을 "예상 변화 방향과의 코사인 유사도"로 바꾸기 — 실제 웹캠에서 R/G/B Δ부터 확인한 뒤 결정.
- 신호가 부족하면 Hadamard 패턴(매번 화면 절반을 다른 조합으로 켜고 계산으로 분리).

## 8. 해커톤 피치 뼈대 (3분)

1. **문제**: 얼굴·목소리는 더 이상 증거가 아니다($25M 딥페이크 CFO 사건). 구글의 손동작 캡챠도 OBS 정지 이미지 한 장에 뚫렸다.
2. **시연 1 — 공격**: 휴대폰 사진, OBS 녹화 영상을 들이댄다 → 반사 없음·평면 물체로 차단.
3. **시연 2 — 진짜 사람**: 무작위 색과 방향 빛에 얼굴·손이 반응 → 통과.
4. **시연 3 — 오버레이**: 화면 일부를 가리거나 커닝 오버레이를 띄운다 → "화면 일부 가림 의심" (감지 한계 숫자와 함께).
5. **한계를 먼저 말하기**: 실시간 반사 합성 주입·3D 마스크는 범위 밖. 지금 흔한 공격의 비용을 올리는 것이 목표.
